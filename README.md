# Doctor Assistant — Production-Ready Doctor Management SaaS

A production-ready medical/doctor management SaaS consisting of two web applications sharing the same Supabase PostgreSQL database.

## Phase 1 (Current): Doctor Management System

Internal staff (Doctor/Admin + Cashier/Receptionist) manage patients, appointments, payments, and clinic settings with email+password authentication.

## Tech Stack

- **Frontend**: React 19, TypeScript, Tailwind CSS v4, Framer Motion, React Router, i18next (Arabic RTL + English LTR), light/dark themes
- **Backend**: Python 3.13, FastAPI, SQLAlchemy 2.0 (async), Pydantic v2, Alembic, JWT auth
- **Database**: Supabase PostgreSQL (single source of truth)

## Getting Started

### 1. Database Setup (Supabase PostgreSQL)

The schema is defined in `backend/migrations/001_initial_schema.sql`.

**Option A — Supabase SQL Editor (recommended):**
1. Go to your Supabase project → SQL Editor
2. Copy the contents of `backend/migrations/001_initial_schema.sql`
3. Run it

**Option B — Alembic:**
```bash
cd backend
venv\Scripts\python -m alembic upgrade head
```

The migration creates:
- 6 tables: users, patients, appointments, visits, transactions, clinic_settings
- Enums for roles, statuses, payment methods, transaction types
- Auto-invoice generation with YYMMDD + daily sequence trigger
- Auto patient visit counting trigger
- Row Level Security on all tables
- Default admin user: `admin@doctor.com` / `admin123` (CHANGE THIS ON FIRST LOGIN)

### 2. Backend Setup

```bash
cd backend
# Create venv (if not exists)
python -m venv venv

# Activate and install
.\venv\Scripts\activate
pip install -r requirements.txt

# Configure environment
copy .env.example .env
# Edit .env with your Supabase DB URL + a strong SECRET_KEY

# Run migration (Option B)
python -m alembic upgrade head

# Start server
python run.py
```

### 3. Frontend Setup

```bash
cd frontend
npm install

# Configure environment
copy .env.example .env
# Edit with your Supabase URL + key + VITE_API_URL

# Dev server
npm run dev

# Production build
npm run build
```

## Authentication

Internal staff use email + password (JWT tokens). The backend enforces RBAC:

- **Admin**: full access — dashboard, patients, appointments, cashier, analytics, settings, user management
- **Cashier**: reception — today's appointments, patients, payments, receipts

Passwords are stored as bcrypt hashes. Never plain text.

## Invoice Numbering

Invoices use a deterministic, database-guaranteed format: `YYMMDDNNNN`
(e.g. `2609010001` = year 26, month 09, day 01, sequence 0001).

Generated by DB trigger `generate_invoice_number()` using a Postgres sequence — collision-safe and concurrency-safe. The frontend cannot generate or manipulate invoice numbers.

## API Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | /api/v1/auth/login | - | Login |
| GET | /api/v1/auth/me | any | Current user |

## Security

- bcrypt password hashing (never plain text)
- JWT with server-side secret
- RBAC enforced server-side (never trust the frontend)
- SQL injection protection via SQLAlchemy ORM + parameterized queries
- Row Level Security enabled on all tables
- Invoice uniqueness enforced by DB constraint + sequence trigger
- Appointment conflict prevention via unique constraint
- Medical data never publicly accessible; RLS policies require service-role
